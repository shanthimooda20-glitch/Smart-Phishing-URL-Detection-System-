How the detector works

The full pipeline, its measured performance, and where it falls short.

Pipeline
1
ValidateOnly http/https URLs of a bounded length with a syntactically valid host are accepted.
2
CanonicaliseThe scheme and a leading www. are stripped and recorded separately, so a URL you type is measured the same way as the corpus the model learned from.
3
Extract 28 featuresLengths, character counts, entropy, subdomain depth, keyword hits, TLD reputation and shortener detection.
4
ClassifyThe trained model returns P(phishing). Thresholds turn it into Safe / Suspicious / Phishing.
5
ExplainEach top feature is re-scored against its training median to measure what it did to this prediction.

Safety model
✓Submitted URLs are treated as strings: never fetched, resolved, rendered or executed.
✓Queries are parameterised through SQLAlchemy; sort and filter values are whitelisted.
✓All output is escaped by Jinja’s autoescaping, so a hostile URL cannot inject markup.
✓Input length and request body size are bounded; stack traces are never returned to the client.
Known limitations
⚠The model sees only the URL string — it has no notion of domain age, reputation, WHOIS data or page content.
⚠Legitimate URLs with hyphenated domains, deep subdomains or short cryptic paths can land in the Suspicious band.
⚠A phishing page hosted on a compromised, ordinary-looking domain is largely invisible to lexical analysis.
⚠The corpus is a historical snapshot; phishing tactics drift, so the model needs periodic retraining.
